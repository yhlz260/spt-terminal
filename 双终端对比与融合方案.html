双终端对比与融合方案

quant-dashboard/trading-dashboard.html  vs  stock-workbench
源码级比对 · 2026-09-14 · 两侧均为单文件 HTML 应用

结论：stock-workbench（B）在逻辑质量上明显更强，trading-dashboard（A）在数据鲜活度与覆盖面更广。两者是同源两代，应"以 B 为内核、以 A 为血脉"合并，而不是二选一。

A 拥有 B 没有的实时抓取能力、全市场雷达、组合风控与择时开关页；B 拥有 A 完全没有的信号实证内核（16 个信号 × 395 只 × 528 交易日的回测胜率/盈亏比/期望收益）、政策可验证的择时门（全市场 pos60 均值 + 20 日动量，附 IC −0.31 依据）、更严的排雷阈值、以及真实持仓→纪律审计→因子审计的完整闭环。A 的信号仍是规则式硬编码，未经任何统计检验。

三、三处根本性逻辑冲突

冲突 1（最要命）：仓位口径不统一

A 的 tierWeights = {mid:0.15×mult, swing:0.05×mult, short:0.03×mult} 是单票占总资金的比例；B 的 rules:{mid:0.5, swing:0.3, short:0.2} 是三层之间的资金分配。同一个"三重仓"，一个说 15% 一个说 50%，两边的模拟仓、风控上限、仓位建议全部不可比。

必须二选一。以你实际使用的 5/3/2 为准（埋伏 50 / 波段 30 / 短线 20），把 A 的 15/5/3 降级为"单票上限"含义。

冲突 2：信号判定哲学不同（规则 vs 实证）

A 的信号是"书上这么写的"——S33 回踩好K 就是好K，不问你历史胜率多少。B 的信号是"数据说它有效"——同一个 S33 有 4478 次样本、胜率 56.4%、期望收益 2.85，而且 S10 爆量震仓因为样本为 0 被直接淘汰。B 的做法直接回答了"这个信号到底赚不赚钱"，这是 A 完全缺失的一层。

方向：以 B 的 SIGNAL_BACKTEST 为准，A 的规则只保留为"信号命名与触发条件的实现代码"。

冲突 3：数据策略两个极端

A 全实时、零底座 → 接口一挂全页空白（你打开看到的满屏"—"就是这个）；B 全静态、有底座 → 数据锚定在 09-11，今天 09-14 已经隔了 1 个交易日，再有道理的逻辑也是旧数据。

方向：实时优先、快照兜底、回落时明确标注而不是留白。快照由每日收盘任务自动回写。

四、各自不可替代的强项

A 只此一家

  • 全市场雷达：涨幅/成交额/概念板块三个动态榜，覆盖 5000+ 只而非仅自选池
  • 组合风控 P2：行业分散、60 日相关性矩阵、等风险贡献权重——B 完全没有
  • Regime 策略开关页：把"当前可开策略 / 当前禁用策略"显式列成清单，最适合盘中快速对照
  • 解禁事件实时抓取：东财 datacenter 接口直连，B 只有手工快照
  • 自动股池接机器人产物：与你现有 RPA 管线（daily_poll / quant_bot）打通

B 只此一家

  • 信号实证内核：16 信号的 EV / 胜率 / 盈亏比 / 样本数，且带防作弊声明（t 日收盘信号 → t+1 开盘成交 → 持有 N 日结算，无未来函数）
  • 实证择时门：pos60 + 动量双因子，附 IC 与分档收益数据
  • 纪律审计：追高率、超止损、接近止损、流水评分——直接审计"你自己有没有守纪律"
  • 策略审计 7 项：剔除 Top5/Top10 后 EV、随机基准对照、最坏入场压测
  • 内置个股详情页：分时/K线/筹码峰/财务/公司 + 持仓调整，不用跳外部文件
  • 使用说明（新手白话版）：把专业名词翻成大白话
  • 洗盘 vs 出货 5 维判定：位置/量能/均线/筹码/K线联合打分

五、融合后的目标架构

层职责合并方式
数据层实时优先 · 快照兜底 · 明示来源A 的东财/腾讯抓取 + B 的内嵌快照底座。抓到→标"实时"；失败→回落快照并标"收盘(09-11)"，不留白。快照由每日 15:30 任务重写。
信号内核实证优先 · 规则执行用 B 的 SIGNAL_BACKTEST + signalConfidence() 给 A 的 sigOfStock() 每个信号加权排序，noise 与 n<30 的不输出。
排雷层P0 三层独立页B 的五指标 + 硬排除阈值（并集）→ A 的独立页框架；A 的实时解禁抓取并入 P0-1。
仓位引擎唯一口径总仓上限取择时门（Regime / MARKET_GATE 二选一，建议用 B 的实证版）；层内 5:3:2；单票上限 = 层内均分 × 1.5。
闭环层台账 → 纪律 → 审计B 的持仓台账 + 纪律审计 + 因子审计；A 的推荐跟踪（localStorage）保留作"推荐质量"独立指标。
扩展页雷达 + 组合风控整体迁入 A 的全市场雷达、组合风控 P2、Regime 策略开关页。

六、落地步骤（按依赖顺序）

1
先定口径把仓位统一为「总仓 = 100% × 择时上限；层内 5:3:2；单票 ≤ 层内均分 ×1.5」。只改一处换算函数，其余视图全部引用它。这一步不做，后面所有对比都是错位比较。
2
接信号置信度在 A 的 sigOfStock() 输出里，给每个信号补 {sigId:'S33', conf: signalConfidence('S33_回踩好K入场')}，排序键从"固定优先级"改为"置信度降序"，conf===0 直接不渲染。
3
数据双源回落fetchQuote() 失败分支从 return null 改为 return SNAPSHOT[code]，并带 src:'cache' 标记；所有渲染把"—"替换成"快照值 + 来源角标"。
4
合并排雷把 B 的 FUNDAMENTAL_SCREEN / FUNDAMENTAL_SCREEN 阈值与 A 的 P0-1 实时解禁合成一个 P0 页；硬排除取并集（净利暴雷 / 高波动 / 质押>10%）。
5
迁入独有页A → B：全市场雷达、组合风控 P2、Regime 策略开关。B → A：因子审计、纪律审计、使用说明、个股详情页。
6
快照自动化 + 版本收口把内嵌快照改为每日 15:30 由脚本重写的 JSON 区块（复用你现有 daily_poll 链路）；去掉 ?v=weakfix 这类补丁参数，改成页脚显示 build 号与快照日期。

七、必须先处理的坑

代理风险A 的兜底通道是 http://127.0.0.1:9091。从 https:// 的 GitHub Pages 打开时，https 页面请求 http 本地端口属混合内容，各浏览器策略不一、极易被拦。建议直接删掉代理分支，只走东财/腾讯公开接口，或把代理换成 https。
快照过期B 的数据锚定 2026-09-11，今天 09-14 已隔 1 个交易日。合并前必须先跑一次回填，否则再强的逻辑也是旧数据。
移动端A 的表格是 white-space:nowrap 且无横向滚动容器，手机上必然溢出。B 有移动端 media query，迁移时以 B 的写法为准。
主题一致性A 是浅色主题，但搜索建议下拉框用了深色配色（#e0e6f0 文字 + #252d48 边框），局部突兀，合并时统一到浅色变量。
外部依赖A 的个股详情跳外部 stock_page.html，B 是内置的。合并后统一用内置详情弹窗，避免再维护第二个文件。
